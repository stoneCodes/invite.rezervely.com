# invite.rezervely.com — Invitations de mariage animées

Service en libre-service : les mariés choisissent un template, remplissent un formulaire avec aperçu en direct, publient, et envoient un lien privé (`/i/<slug>`). Les invités ouvrent une invitation animée et répondent (RSVP). Les mariés suivent les réponses dans leur espace (`/espace/<token>`).

Marque visée : **joyeuxevent** (décidé avec Glad le 6 nov. 2026). Les mariages d'abord ; plus tard d'autres événements (anniversaires, baptêmes, fiançailles…) : éviter de figer « mariage » dans le code quand c'est facile. Logo choisi par Glad le 6 nov. 2026 : piste « Étincelle » (« joyeux » ivoire + « event » or en Jost, deux étincelles or et rose). Fichiers dans `public/brand` (texte vectorisé), composant `components/Logo.tsx`, icônes `app/icon.svg` et `app/apple-icon.png`.

Propriétaire : Glad (francophone, veut des retours honnêtes et des listes à puces). Toute l'interface est en français.

## Stack
- Next.js 15 (App Router, TypeScript), hébergé sur **Cloudflare Workers** depuis le 6 nov. 2026 (adaptateur `@opennextjs/cloudflare`, Worker `joyeuxevent`, compte Cloudflare Glesucces, formule gratuite ; passer à Workers Paid 5 $/mois dès les premiers paiements ou au premier « Exceeded CPU Time Limits » dans Metrics). Relié au dépôt GitHub (Workers Builds) : build `npx opennextjs-cloudflare build`, déploiement `npx opennextjs-cloudflare deploy` à chaque push sur `main`. Config : `wrangler.jsonc` (variables non secrètes, cron, `keep_vars: true` pour ne pas effacer les secrets du tableau de bord), `open-next.config.ts`, `worker.ts` (entrée : site + tâche planifiée). Domaine `joyeuxevent.com` (acheté chez LWS, DNS chez Cloudflare, serveurs `kyle`/`veronica.ns.cloudflare.com`) attaché au Worker en domaine personnalisé ; `www` redirige en 301 (règle « Redirect from WWW to root »). Adresse de secours : https://joyeuxevent.glesucces.workers.dev. L'ancien projet Vercel (`iccgospel`, https://inviterezervelycom.vercel.app) reste en secours sans domaine ; retour arrière = remettre A `@` → 216.198.79.1 et CNAME `www` → Vercel après avoir retiré les domaines du Worker.
- Supabase (projet `usolfegmepnazrporeec`) : Postgres + Storage (bucket `photos`). Schéma : `supabase/migrations/001_init.sql`.
- Pas de client Supabase côté navigateur : RLS activé **sans policy**, tout passe par les routes serveur avec la clé `service_role` (`lib/supabase.ts`, marqué `server-only`).
- Variables : voir `.env.example`. Non secrètes dans `wrangler.jsonc` ; secrets (`SUPABASE_SERVICE_ROLE_KEY`, `BREVO_API_KEY`, `CRON_SECRET`) saisis par Glad dans Cloudflare (Worker → Settings → Variables and secrets, type Secret), jamais dans le chat. Local sur le moteur Cloudflare : `.dev.vars` (non versionné) + `npm run cf:preview` ou la config `cf` de `.claude/launch.json` (port 8787).

## Structure
- `components/invitation/` : le cœur visuel.
  - `engine.js` : moteur porté du prototype validé (ouvertures, particules, défilement scénarisé, grattage, dress code, verset, musique synthétisée). `mountInvitation(data, template, opts)` → `{ replay, destroy }`. Fichier JS volontairement non typé (typage dans `engine.d.ts`).
  - `markup.ts` : balisage commun aux 3 templates (les ids sont utilisés par le moteur).
  - `invitation.css` : styles des 3 templates (tokens par `body[data-tpl]`).
  - `Invitation.tsx` : composant client qui monte le moteur. Pour changer les données, remonter le composant (prop `key`). Aiguille selon le template : `appel` → `appel/appel.js` (`mountAppel(root, data, opts)`), les autres → `engine.js`.
  - `appel/` : moteur « Appel entrant » (écran d'appel → conversation), styles préfixés `ap-`, images `public/img/appel-*.webp`. Mêmes options (`onRsvp`, `skipIntro`, `noGate`) ; dans l'aperçu de l'éditeur, tout s'affiche d'un coup.
  - `boule/` : moteur « Le monde miniature » (`boule-neige`), styles préfixés `bn-`, images `public/img/boule-*.webp`. Boule à secouer (capteur de mouvement, autorisation au toucher sur iPhone, glisser au doigt ou bouton en repli), plongée, puis une scène par section (caméra qui avance au défilement). Date = buée à essuyer. Les repères des images (sphère, cadre du chevalet, étapes du chemin, porte du domaine) sont en tête de `boule.js` : à remesurer si une image change. Les fleurs du cadre du chevalet sont reposées par-dessus la photo des mariés (`public/img/boule-chevalet-fleurs.webp`, fabriquée par `images-source/boule-chevalet-fleurs.py`) pour que la photo ne déborde jamais du cadre.
  - `origami/` : moteur « Origami », styles préfixés `or-`, images `public/img/origami-*.webp`. Grue en 8 facettes (SVG) qui se déplie en feuille ; pliages CSS 3D (carte en deux, accordéon du programme, carte en trois du lieu) dépliés à l'arrivée à l'écran ; date dans une enveloppe à 4 rabats ; réponse envoyée en avion en papier.
  - `velours/` : moteur « Éclat de velours », images originales `public/img/velours-enveloppe.webp` (ouverture plein écran) et `public/img/velours-serre.webp` (décor intérieur). Enveloppe scellée bordeaux qui s'ouvre dans un éclat champagne, puis même ordre et même contrat que les autres modèles (retravaillé le 7 nov. 2026) : date sous une feuille d'or à gratter obligatoire, couleurs du dress code cliquables hommes/femmes avec couple réaliste, musique (valse synthétisée) + bouton son, itinéraire + agenda, RSVP (0 invité si « non »). Styles préfixés `ve-`, textes dans `inviteDict(lang).velours`.
- Nouveau template = ajouter son id dans `lib/types.ts` (TEMPLATES), `app/i/[slug]/opengraph-image.tsx` et une migration SQL qui élargit la contrainte `invitations_template_check` (ex. `002_template_appel.sql`), ainsi que son thème PDF dans `lib/pdf/themes.ts` et sa photo de démo dans `lib/demoPhotos.ts` (le typecheck échoue sinon). Le modèle `velours` est autorisé par `supabase/migrations/010_template_velours.sql`. Sa démo Ahmed/Fatima utilise `public/img/demo-couple-velours.webp` et un exemple de verset Ar-Rûm 30:21.
- `app/creer/Editor.tsx` : éditeur (formulaire + iframe `/apercu` alimentée par `postMessage`), modèle choisi mis en avant ; toucher une carte ouvre la démo de ce modèle avec les infos des mariés (flèches pour parcourir, « Choisir ce modèle ») ; « Voir le rendu » = 2e iframe `/apercu?plein=1` en plein écran (ouverture complète, données non enregistrées comprises).
- `app/i/[slug]` : page publique + image Open Graph (aperçu WhatsApp).
- Liens lisibles (décidé avec Glad le 6 nov. 2026) : à la 1re publication, l'invitation reçoit `joyeuxevent.com/lea-et-samuel-k7m2` (prénoms sans accents, « et »/« and » selon la langue de l'invitation, un seul prénom → `lea-k7m2`, + code de 4 caractères pour les homonymes ; nouveau tirage si déjà pris). Fixé ensuite pour toujours (`lib/publish.ts`), même si les prénoms changent. Servi par `app/[slug]` (les routes fixes passent avant) ; les anciens liens `/i/<code>` marchent toujours. Toujours construire un lien avec `invitePath(slug)` (`lib/slug.ts`).
- `app/espace/[token]` : réponses, stats, export CSV ; `/voir` montre l'invitation aux mariés (publiée ou non, réponses non enregistrées).
- `app/api/*` : création/mise à jour (`invitations`), publication, envoi photo, RSVP.
- `lib/validate.ts` : nettoyage/bornage de toutes les données venant du client. Toute nouvelle donnée doit y passer.
- `prototype/index.html` : prototype d'origine validé par Glad (référence visuelle ; ses images sont dans `public/img`).

## Décisions validées avec Glad
- 3 templates pour démarrer : `cygnes` (Lac aux cygnes), `nuit-doree` (Nuit dorée), `jardin-nuit` (Jardin de nuit). Chacun a sa propre ouverture ET sa propre mise en page.
- Ordre de l'invitation : « Nous nous marions » + prénoms (sans date) → photo + verset → **date à gratter obligatoire** (la suite est masquée tant que la date n'est pas grattée) → compte à rebours → programme → dress code → lieu → histoire → RSVP.
- Verset facultatif (Bible, Coran, autre), saisi librement par les mariés, texte original (ex. arabe, RTL) + traduction + référence. Ne pas fournir de versets pré-remplis sans relecture.
- Dress code : 1 à 4 couleurs de n'importe quelle teinte, possibilité d'une couleur différente hommes/femmes, consignes libres. Veste et robe en SVG recolorées.
- Effets « waouh » au défilement sur les 3 templates (héros épinglé qui avance dans la scène, médaillon photo en 3D avec orbite de particules, titres lettre par lettre, fil lumineux du programme…).
- Textes, images : pas de texte ni de visage dans les images générées par IA ; images en WebP dans `public/img`.
- Photos de démo (décidé avec Glad le 7 nov. 2026) : une photo de couple par modèle (`public/img/demo-couple-<id>.webp`, `lib/demoPhotos.ts`), exception voulue à la règle « pas de visage ». Affichée **uniquement** dans les démos (`/demo/<id>`, pop-ups de l'accueil, autres modèles parcourus depuis l'éditeur) quand il n'y a pas de photo des mariés (prop `demoPhoto` de `Invitation`). Jamais dans une invitation publiée, l'aperçu de l'éditeur, « Voir le rendu » ou `/voir` : sans photo, la silhouette dessinée reste.
- Démo : les barres de navigation, boutons de retour et fonds de la fenêtre plein écran suivent la palette claire ; le rendu de l'invitation dans l'iframe conserve le thème propre du modèle.
- Dress code réaliste (décidé avec Glad le 7 nov. 2026, fait pour les 7 modèles, velours compris) : module `components/invitation/dresscode/couple.js` (`coupleHtml`, `mountCouple(el, id).set(homme, femme)`, cravate = couleur de la robe), images `public/img/dresscode-<couple>.webp` + masque `-mask.png` (rouge costume, vert robe, bleu cravate), fabriqué par `images-source/dresscode-masque-*.py`. **Visuel par défaut partout : `tenues`** (costume trois pièces + robe longue seuls, sans personne ni visage, choisi par Glad le 7 nov. 2026, masque `images-source/dresscode-masque-tenues.py`) ; le couple `afro` reste disponible dans `COUPLES` mais n'est plus affiché ; ajouter un couple = l'entrée dans `COUPLES` puis un choix dans l'éditeur (champ `dressCode.couple`, à passer dans `lib/validate.ts`). remplacer la veste et la robe dessinées par une photo réaliste d'un couple en pied, tenues gris clair neutre recolorées en direct dans le navigateur (masques costume / robe / cravate-pochette, plis et ombres conservés). Deux couples au choix des mariés : style européen et style africain. Visages acceptés pour cette image (exception à la règle « pas de visage »). Aucun texte dans l'image : titres, noms des couleurs et consignes restent en texte (FR/EN). Pastilles de couleur en satin recoloré.
- Identité du site (accueil, éditeur, espace, admin) : palette claire blanc cassé et beige doré validée par Glad le 7 nov. 2026 ; texte foncé, boutons beige doré, logo « joyeuxevent » renforcé en gras. ## Langues (FR/EN, décidé le 6 nov. 2026)
- **Site** (accueil, éditeur, espace, API) : langue choisie par le bouton FR/EN (`components/I18n.tsx`, `LangSwitch`), mémorisée dans le cookie `lang` (sinon langue du navigateur). Serveur : `getT()` / `getLang()` (`lib/i18n/server.ts`) ; client : `useT()`.
- **Invitation** : langue choisie par les mariés dans l'éditeur (champ `data.lang`, `fr` par défaut), indépendante du site. Textes fixes dans `lib/i18n/invite.ts` (`inviteDict(lang)`, importé aussi par les moteurs .js). Les textes saisis par les mariés ne sont jamais traduits.
- Dictionnaires : `lib/i18n/site-fr.ts` (référence) + `site-en.ts` typé `SiteDict` ; `invite.ts` typé `InviteDict`. Une clé ajoutée en français sans anglais fait échouer `npm run typecheck` : c'est la garantie.
- **Règle** : aucun texte visible écrit en dur dans un composant, un moteur, une route API ou un e-mail. Toute nouveauté (modèle, page, e-mail, message d'erreur) ajoute ses clés FR + EN. Dates : `LOCALE[lang]` et `dateParts(iso, lang)`.
- Ajouter une langue = l'ajouter dans `LANGS` (`lib/i18n/index.ts`) + un dictionnaire de chaque type.

- Migration `005_emails.sql` (`owner_lang`, `rsvps.notified_at`) : à appliquer **avant** de déployer le code (sinon la création d'invitation échoue).

## Espace administrateur
- `/admin` : connexion par code e-mail (6 chiffres, 10 min, usage unique, 5 essais), session signée de 12 h, vérification serveur et 404 sans session. `/administrateur` redirige vers `/admin`; routes/pages exclues des moteurs de recherche.
- Tableau de bord d'activité : périodes aujourd'hui / 7 jours / 30 jours / depuis le début ; agrégats calculés par la fonction SQL `admin_dashboard`.
- Le filtre de période du tableau de bord est un formulaire GET natif (page serveur), sans gestionnaire client dans le rendu serveur.
- Les indicateurs du tableau de bord sont interactifs : au clic, une fenêtre modale affiche les valeurs détaillées et jusqu'à 50 invitations récentes correspondant à la période ; les invitations ouvrent leur fiche admin.
- Migration `007_admin.sql` : à appliquer dans Supabase > SQL Editor **avant le déploiement** du code de l'étape 1. Elle ajoute les tables privées `settings`, `admin_codes`, `admin_events`, `comped_at`, `keep_until` et les agrégats du tableau de bord.
- Secrets à saisir directement dans Cloudflare Worker `joyeuxevent` > Settings > Variables and secrets (type Secret) : `ADMIN_EMAILS` (adresses séparées par des virgules) et `ADMIN_SESSION_SECRET` (32 caractères aléatoires minimum). En local, les placer dans `.env.local`.
- Étape 2 : liste paginée (50 invitations), filtres et recherche ; fiches détaillées avec réponses paginées ; actions offertes, renvoi du lien, dépublication, prolongation et suppression confirmée. Les mutations sont en POST, protégées par session + Origin et journalisées dans `admin_events`. La purge respecte `keep_until`.
- La suppression d'une invitation est aussi proposée dans les détails accessibles depuis le tableau de bord et dans la liste des invitations. Elle demande une confirmation puis la saisie de `SUPPRIMER`, supprime les photos, réponses et invitation, et laisse une trace dans `admin_events`.
- `/admin/clients` regroupe les invitations par adresse e-mail, recherche par adresse ou prénom, donne le nombre de réponses et l'activité récente, et permet de gérer chaque invitation. La migration `008_admin_clients.sql` doit être appliquée dans Supabase > SQL Editor avant de déployer cette page.
- La page clients limite les informations disponibles aux données existantes. Pistes affichées pour évolution : fiche unifiée, export des données, demandes RGPD, notes de support et historique des échanges.
- Étape 3 (partie prix et codes promo) : `settings.price_cents` pilote l'affichage du prix et le montant Checkout ; `settings.payments_enabled` pilote le bouton d'activation admin et prévaut sur `PAYMENTS_ENABLED` (utilisé comme valeur par défaut). Les codes créés dans Stripe restent acceptés au Checkout ; le dernier code valide créé est annoncé sur l'accueil jusqu'à son expiration.
- `/admin/prix` présente le prix, un bouton pour activer/désactiver les paiements, le mode Stripe, les formulaires tarif/promo et la liste des codes. L'activation est bloquée si aucune clé secrète au format Stripe test/live n'est configurée.
- Étape 4 : `/admin/statistiques` lit Cloudflare Web Analytics via GraphQL côté serveur, avec cache de 5 min, périodes 7/30 jours, visites/pages vues, pages, référents, pays, appareils, navigateurs et entonnoir avec les agrégats Supabase. Le beacon Cloudflare est chargé sur les pages publiques seulement, jamais sur `/admin` ni les API.
- La navigation commune de l'admin est une barre latérale à gauche sur grand écran et une rangée horizontale sur mobile ; elle donne accès au tableau de bord, aux statistiques, aux invitations et au prix, avec la page active mise en évidence.
- Pour activer les statistiques, configurer `CF_ACCOUNT_ID` et `CF_WEB_ANALYTICS_SITE_TAG` comme variables non secrètes et `CF_API_TOKEN` comme secret (permission Account Analytics: Read) dans Cloudflare ; les noms sont aussi documentés dans `.env.example`. Sans ces variables, l'admin affiche les instructions de configuration.
- La politique de confidentialité FR/EN mentionne Cloudflare Web Analytics dans « Cookies et stockage local ».
